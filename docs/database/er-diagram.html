The SellMore flow, from the start

Follow one company from sign-up to practice. Each point says what happens, then lists every table it uses and the columns that matter there. Click a table name to find it in the diagram above.

Set up the company

  1. 1

    A company is created on a plan

    The super admin creates the company and picks a plan. The plan decides the seats, the monthly meeting quota, the monthly credits and which features are on. Upload limits come from the platform limits, stored as one key and value per row. A plan can offer a free trial of a set number of days, and the company records when its trial ends. Every table also has created_at and, where rows change, updated_at. Tables that people edit record created_by, updated_by and, where rows are hidden, deleted_by, stamped by the database from the signed-in user.

    The plan the company is on. It is only read here.

    • trial_days length of the free trial in days, empty means the plan has no trial
    • seat_limit most active users, empty means unlimited
    • meeting_quota meetings per month
    • monthly_credits credits granted each month
    • price_monthly
    • currency
    • active
    • created_by the platform owner
    • updated_by

    One row per feature the plan includes. The app checks these before showing a feature.

    • plan_id
    • feature_key e.g. crm_sync, drive_sync, live_assist, mock_meetings, deal_practice, practice

    Upload and invite rules that every company shares, stored as one key and value per row. A new limit is a new row, no schema change.

    • limit_key e.g. allowed_formats, max_file_size_mb, max_duration_min, invite_expiry_hours
    • limit_value the value, as JSON
    • description
    • updated_by the platform owner

    The company itself. Every other table points back to this row through client_id.

    • updated_by

    The super admin who does this. Platform owners are stored apart from client users and have no company.

  2. 7

Drive route: each weekday evening the audio is copied to the Drive folder "Call recordings", and SellMore matches the file to the waiting meeting. Upload route: a rep uploads a file directly. What each role can reach

Every business table carries client_id (tables that belong to one person, such as deals, meetings, practice, mock meetings, chats and notifications, store that person in client_user_id instead and take the company from them), and the database itself (row level security) checks the role on every query. A rep's team is never stored twice: it comes from client_users.manager_id.

Super admin

stored in platform_owner_users

Runs the platform: plans, limits, default cues, clients. Sees no meetings, deals or documents. Gets seat and meeting counts only, through the client_usage view.

Client admin

client_id = own client

Everything inside their company: users, integrations, documents, knowledge, billing, every lead and call.

Manager

client_user_id IN (client_users WHERE manager_id = me)

Their assigned reps' leads, calls, lessons and mock meetings. Can build lessons for a rep and leave feedback.

Sales rep

client_user_id = me

Their own leads, calls, lessons, mock meetings and chats. Cannot see colleagues' data.

Design choices

One company boundary

client_id sits on every business table, so one query filter (and one database policy) keeps companies apart. Only super admins have no client.

A call without a lead

meetings.lead_id may be empty. Linking an orphan call to a new lead only sets that column. Leads typed in by hand use source = draft and leave the CRM columns empty.

Cues: defaults and overrides

Platform defaults have no client_id. A company's replacement points back through overrides_cue_id. Calls score against the cue row that was in force, so history stays true.

Lessons store the cues, not the script

A lesson is a title plus its cue set (practice_lesson_cues) and where it came from. The conversation is rebuilt from templates, so improving a template improves every lesson.

Calculated, not stored

A manager's team, a lead's call count and days in stage, a cue average, a client's seats and meetings used, and a source's citation count are views (lead_stats, client_usage, knowledge_usage). Storing them invites numbers that disagree.

A call has two sources, one meeting

Salesforce knows who and when (crm_activities); the Drive folder holds the audio (media_files). meetings joins them, and sits in awaiting_audio until the file arrives. Neither side can import the same call twice.

Companies cannot be mixed up

Links between company tables are composite keys on (client_id, <the table's own id>). A meeting cannot point at another company's rep, deal or file, even if the app has a bug.

Rules live in the database

One manager per rep, in the same company; the plan's seat limit; buyer-only objections; credits that cannot go negative or be charged twice. Each is a constraint or trigger, and tests/verify.sql proves them.

Keys named after their table

Every key is table_id: clients.client_id, meetings.meeting_id, client_users.client_user_id. A join reads the same on both sides, and a link to a table keeps that name (meetings.lead_id points at leads.lead_id).

Who did it, and when

Every table has created_at, and tables whose rows change have updated_at. Tables that people create or edit also keep created_by, updated_by and, for hidden rows, deleted_by. The database stamps them from the signed-in user, so the API cannot forge them. They stay empty for syncs, imports, AI jobs and super admins acting inside a company.

Limits as key and value

platform_limits holds one row per limit: limit_key and a JSON limit_value. A new limit is a new row, with no schema change.

Free trials

A plan sets trial_days (empty = no trial). A company records when its own trial ends in clients.trial_ends_at.

Ledgers only grow

credit_transactions, audit_log and platform_audit_log refuse UPDATE and DELETE. Every manager change is also kept in manager_assignments.

Practice for a deal

AI-built lessons for a deal sit in practice_programs and practice_program_lessons. Lessons a user builds from cues stay in practice_lessons. Attempts and manager feedback attach to either. Call prep, the mock buyer conversation, is separate and lives in mock_meetings.

Raw text, tags and search vectors

Next to the cleaned text sit the raw copy (raw_text, raw_output), lower-case tags and a halfvec embedding for search by meaning, on transcript turns, chat messages, knowledge chunks, company documents and each meeting's summary. When a recording expires, the raw copies and turn vectors of that call are cleared; the cleaned transcript stays.

Not in this map

The audio and document files themselves (object storage, referenced by storage_key), the speech-to-text and analysis workers, the login provider, and the embedding model itself (the vectors are stored, the model that makes them is a service).
